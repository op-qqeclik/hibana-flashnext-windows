# 06 · 复盘：四天、45 轮、一次自我推翻

> **English abstract** — The postmortem. What worked (gates before claims, engine-internal CUPTI over
> microbenchmarks, A/B interleaving, honest ceilings), what failed (we built the validation set *after*
> training 23 draft heads, and spent a day celebrating a +11 % that was memorisation), the three times the
> measurement method fooled us, the four counter-intuitive findings worth carrying to the next platform, and
> the checklist we wish we had on day one.

## 1. 做对的五件事（下次直接抄）

### 1.1 先建闸门，再谈优化

每一次"变快了"都必须先过 `refcheck.py cmp base`（位一致，md5 相同）再谈速度。
这条纪律挡住了所有"用质量换速度"的诱惑（也当场否掉了 `--throughput` profile：接受率 0.597 → 0.4445）。

### 1.2 用引擎内 CUPTI，不信孤立微基准

自建微基准说"加 split-K 有 1.9–2.5 倍收益"，打上补丁后引擎内实测 **12.6 → 26.5 µs（慢 2 倍）**。
原因：单次 `w3_linear` 的 Python 发射开销 20–40 µs，而 GPU 实际只有 12 µs —— **微基准测的是主机侧**。
⇒ 所有内核级结论都必须用 `HIBANA_PROFILE_STEPS` 的引擎内窗口复核。

### 1.3 A/B 必须交错，两臂背靠背

这张卡有 co-tenant（ComfyUI / Strata），GPU 频率随桌面负载漂移。
"上午测 A、下午测 B"给出的差异可以完全是环境差异。交错各 2–3 次取中位是唯一可靠做法。

### 1.4 找"静默降级"，而不是先调参数

引擎按平台名把关（`if cap == (12, 1)`），在 107（`(12, 0)`）上**静默关掉了一批图融合**。
一行改动拿到 code +8.6%、接受率 +0.046。
⇒ 移植后第一件事：`grep -rn "12, *1\|sm_121\|GB10"` 把平台判定全找出来。

### 1.5 天花板要算，但算出来的天花板要敢被实测推翻

我们按"每轮 49 GB 专家流量 ÷ 1.6 TB/s"算出 c16 上限 1690。最终实测 **2035**（120%）。
⇒ 天花板是**排期工具**（告诉你哪条路不值得走），不是**事实**。写进文档时标明它是估算。

## 2. 做错的四件事（这一节比 §1 值钱）

### 2.1 ★ 先训了 23 个草稿头，才想起建验证集

顺序完全反了。正确顺序是：

```
冻结宽集（120 条，句式与训练语料不相交）  →  再训第一个版本  →  每版都用它裁决
```

我们做的顺序是：训 v2…v23 → 用 3 条散文 prompt 看到 +11% → 高兴 → 建宽集 → **全部归零**。
代价：一天半 + 23 个 5.2 GB 的权重。

### 2.2 把"留出集"当成了"泛化集"

v5/v8/v9 在 75 条散文留出序列上 `accept_len` 2.668 → 2.904 → **3.017（+13.1%）**，单调上升、跨语料。
我们据此认定"v9 更好"。但它只证明"**在散文分布内更准**"，没证明"**在新题面上更准**"。
留出集和训练集**语料同源**时，这个指标会给出**虚假的 +13%**。
⇒ 真正的泛化集要换**语域 + 句式模板**，不只是换句子。

### 2.3 把 trainer 指标当成了线上收益

`accept_len` 2.6 → 3.0 是真实的（在同一分布上），但它**不蕴含**吞吐提升。
窄域内两者相关，宽域内不相关。对外只应报**引擎侧宽集数字**。

### 2.4 让 loss 主导了训练判断

小 batch（有效 8）下，单步 loss 在 0.63–1.39 抖动、**无下降趋势**。
而 2 epoch 那次 loss 没降、`accept_len` 却涨了（3.885 → 3.932 → 3.939）。
⇒ **训练中唯一可用的信号是 held-out 的行为指标**，不是 loss。

## 3. 三次被测量方法骗（每次都花了半天以上）

| # | 我们以为 | 实际 | 教训 |
|---|---|---|---|
| 1 | 窄集 +11~19% 是蒸馏收益 | `c1_prose.py` 的 3 条 prompt 与训练语料 `TECH_DOMAINS` **第 2/4/3 条逐字重叠**，测的是记忆 | **验证集必须与训练语料做字面重叠检查**（`grep` 每一句） |
| 2 | split-K 微基准 1.9–2.5× | 微基准测的是 Python 发射开销（20–40 µs）而非 GPU（12 µs） | 内核结论必须引擎内复核 |
| 3 | 冷启动后 c8 掉到 129 | PLE 页缓存是冷的；暖机后 171+ | 所有测量先暖机，且报告里要写"第几轮" |

**共同结构**：三次都是**测量工具本身在测别的变量**。所以这套流程里最贵的东西不是代码，
是 §4 那张"引用规则"。

## 4. 数字纪律（引用这份仓库时的规则）

1. **每个数字必须带：日期 + 口径（贪心/采样）+ prompt 集 + 是否暖机。**
   缺一个就不要引用。
2. **跨 prompt 集不可比**（同一个头在不同集上差 19%）。
3. **贪心与 temp 0.3 不可混表**（差 15–27%，是解码差异不是稳定性）。
4. **同一指标多版本时，以"带仪器 + 带日期"的为准**（见 `docs/04` §9.5 的口径演变表）。
5. **被推翻的数字保留在文档里**，标【已作废】—— 它们是方法论的证据。

## 5. 四个反直觉发现（值得带到下一个平台）

### 5.1 少读字节 ≠ 更快

把 hyper-connection 从 fp8 换成 bf16：每轮解码字节 **5.38 → 6.01 GB**，速度 **310.6 → 325.6 tok/s**。
原因：fp8 走 `torch._scaled_mm` 的 Ada `sm89_xmma…32x64x64` 瓦片，瓶颈是**内核效率**不是带宽。
这也解释了两件此前没想通的事：为什么"窄 GEMV 接管 sm89"更慢、为什么加 split-K 更慢。

### 5.2 "GPU 气泡"有一部分是假象

早期 `_StepProbe` 报 `wall ≈ gpu`，我们据此以为没有气泡；换 profiler 后发现**两个 event 的跨度
把气泡也包进去了**。只有 profiler 的 device 时间是真实忙碌时间。
⇒ 时间测量工具本身也要被怀疑一次。

### 5.3 Windows 的固定成本是"按次"收的，不是"按字节"

`cudaEventSynchronize` 在 Linux 上 10–30 µs、WDDM 上 **1.85 ms**；`cudaGraphLaunch`（500 节点）
0.4–0.85 ms 且**随节点数线性涨**。
⇒ 在 Windows 上，"少一次同步""少 100 个图节点"比"少读 1 GB"更值钱。

### 5.4 引擎的"平台名判定"是隐形性能损失

一批融合被 `SM == (12,1)` 挡住，代码照跑、日志正常、只是**慢 8%**。
⇒ 移植任何"只在某平台调优过"的引擎，第一件事是把平台判定全列出来。

## 6. 最终账（诚实版）

| 项 | 数值 | 相对目标 |
|---|---|---|
| 单流（c1，宽集贪心） | **273.5** | 60% / 455 |
| 单流散文（en / zh） | **325.6 / 332.3** | 72% / 73% |
| c2 / c4 / c8 / c16 | 527.7 / 724–847 / 1321.8 / **2035.5** | 75% / 78–91% / 84% / **120%** |
| 相对 DGX Spark 生产配方 | 单流 1.8–2.4× / c16 ~3.1× | — |
| 相对移植完成时 | 单流 ×3.0 / c16 ×10.2 | — |

**没达到的部分，原因已经量化到了根上**：

```
c1 = 273 tok/s
   = tok/round 4.11  ÷  round_ms 13.12   （× 1000）
   ↑ 分子：第 2–8 个草稿接受率 0.30（需要 ~0.87 才能到 455）
   ↑ 分母：其中 12.6 ms 是固定权重流量（18–20 GB/轮），主机侧已 −0.1 ms，无处可压
```

⇒ 要 455，**必须换草稿头架构**（块并行 DFlash2 类，且要在本机隐藏态上重训）；
要更高吞吐，**必须把 231 次 trunk GEMV 合并**（改权重布局，作者级）。

## 7. 未解决的 5 件事（交接清单）

1. **≥1 K token 的 prompt 会崩**（`hyper_prefill.mix` 的 `_scaled_mm` 在 SM120 不支持）；修到第二层
   （`qsa_score_exact` 的 JIT 链接）后回退，未闭环。
2. **~50 K token 的长会话 `cached=0`**、每轮全量重算、TTFT 30 s+（怀疑 prompt cache 只有 4.2 GiB
   装不下单条状态 + 系统提示有易变块导致前缀在 21 776 token 处断掉）。
3. **DFlash2 块并行草稿头**权重与引擎特征 tap 不对齐（zh accept 0.066），必须重训。
4. **231 次 trunk GEMV 合并到 ~96 次**：需离线重排 3-bit 量化权重布局（per-row/32-group scale 对齐是主要风险）。
5. **NVFP4 KV / SSD 前缀层 / TP2**：前者编不过，中者未实测收益，后者 Windows 没有 NCCL。

## 8. 如果从零再做一次（10 条 checklist）

```
[ ] 1. 先写"验收口径"文档：哪个 prompt 集、贪心还是采样、几点、几次、要不要暖机
[ ] 2. 冻结宽集（≥120 条，跨语域 + 跨句式），并且和训练语料做字面重叠检查
[ ] 3. 建位一致闸门（refcheck）+ 五点 sweep + 4 分钟 soak，三者缺一不可
[ ] 4. 移植完先 grep 平台判定（12,1 / GB10 / sm_12x），修静默降级
[ ] 5. 先削"按次收费"的东西（同步次数、图节点数），再削字节
[ ] 6. 任何"加速"先问：它减少的是次数还是字节？（Windows 上次数更贵）
[ ] 7. 内核结论只在引擎内 CUPTI 上采信
[ ] 8. A/B 交错、各 2–3 次取中位、报告里写清 co-tenant 状态
[ ] 9. 训练只用 held-out 行为指标裁决；trainer loss 在 batch<32 时没有信息量
[ ] 10. 被推翻的结论写进文档，别删——它是下一轮省时间的唯一凭据
```

## 9. 一句话总结

> **把一套为统一内存写的引擎搬到独立显存的 Windows 上，收益不在"跑起来"，
> 而在认清"这张卡上什么贵、什么便宜"。**
> 这次认清了三件事：WDDM 按次收税、PLE 的主机侧握手是结构性成本、
> 以及 **窄域蒸馏骗得过 trainer，骗不过 120 条新题**。
